# 项目文档撰写规范

业务负责人用文档确认规则，研发与 Codex 据此实现，验收人员凭记录复核结果。写作时点明谁执行动作、动作作用于哪条记录，以及成功或失败后能观察到什么。

## 选择位置

顶层的 [project.md](project.md) 记录项目目标、负责人和系统边界，[readme.md](readme.md) 提供导航，本页维护写作约定。专题文件名使用小写英文单词，多词用短横线连接，例如 `equipment-acceptance.md`。

| 目录 | 主要内容 |
| --- | --- |
| `capability/application/` | 角色、使用场景、操作和用户可见结果 |
| `capability/infrastructure/` | 外部应用身份、网络接入、部署和联调 |
| `api/` | 外部调用方依赖的身份、输入输出、错误和重试契约 |
| `architecture/data/` | 权威存储、字段、约束、索引、迁移和恢复 |
| `architecture/workflow/` | 跨步骤流程，写明触发者、状态变化、提交点和异常恢复 |
| `standard/` | 多个模块共用的约定、验收方法和证据 |

有同层 `template.md` 时，复制为新文件并替换占位内容。每项规则选定一份主文档，其他页面通过相对链接引用。新增、改名或移动专题后，同步更新[项目文档导航](readme.md)。

## 把规则写到可以核对

开头说明读者和用途。步骤用有序列表，字段或状态对照用表格。字段、环境变量和命令沿用代码中的拼写。命令注明执行目录、所需配置和成功时可观察的结果。请求样例使用虚构数据，凭据通过环境变量传入。

以设备验收为例：若负责人已确认重复提交规则，能力文档可写成“经办人用同一提交标识连续提交两次 EQ-001，列表中只有一条待审记录”。接口文档写明第二次请求的响应，数据文档写明唯一约束，验收记录填入两次调用的实际结果。尚未确认的行为标注“待业务负责人确认”；只有实测后才记录“已通过”。

## 随变更更新文档

- 接口输入或输出变化时，同步更新请求与响应样例，写明受影响的错误场景和调用方动作。
- 状态或索引变化时，同步更新数据契约、恢复步骤与验收命令，说明怎样核对已有记录。
- 配置变化时，对照后端与部署目录的 `.env.example`、`compose.yaml` 和部署说明，核对名称、默认值及生效位置。
- 完成验收后，记录日期、版本、隔离数据、预期、实际结果及未验证项。从能力或契约页面链接到对应的[验收记录](standard/acceptance.md)。
